# System observation verification

This reviewed observation workflow uses the separately reviewed observer and selected Python observation. It does not approve a runtime profile, execute either synthetic guard mode, install Lean, acquire proof payloads or claim proof success.

A held-root parent invokes the unchanged native process supervisor with exact LANG, LC_ALL and TZ values. The child is the fixed isolated Python observer, without a credential-bearing environment. The source performs read/hash observations only. There is no new operating-system network or mount configuration in this envelope.

The parent has one CPU affinity, 1 GiB address space, 60 CPU seconds, 64 FDs, a 1 MiB per-file limit, and an original 50-second acceptance deadline. An alarm is scheduled from the remaining original 50-second budget and poisons it on delivery. Handler setup and operating-system scheduling may delay delivery; the exact original Budget checks govern acceptance. The external watchdog sends TERM at 60 seconds and KILL after a further 10-second grace (70-second outer ceiling). TERM/alarm are deferred through the complete native call, including cleanup, and force rejection afterward. A hard-killed or incomplete job is ineligible; the watchdog itself does not prove descendant cleanup. GitHub job/runner cleanup is the fallback, and terminal job success plus the retained native cleanup receipt remain mandatory. The child independently retains the observer's 30-second original deadline, one CPU, 256 MiB address space, 30 CPU seconds, 32 FDs and 1 MiB per-file limit. The native supervisor samples a 256 MiB owned target-tree RSS ceiling and accepts at most 1 MiB combined captured logs. The native timeout is at most 35 seconds, clipped to the parent's original remaining time less the unchanged three-second cleanup reserve, and must leave at least the full 30-second child budget. Parent and child limits are separate: their address-space ceilings conservatively sum to 1.25 GiB, not a combined 256 MiB bound. Actual process execution remains untested by local inert tests.

Three literal upload paths are retained: system-observation.stdout, system-observation.stderr, launch-receipt.json. Each physical file has an independent 1 MiB ceiling. Preflight reserves 4 MiB plus sixteen allocation blocks and sixteen free inodes, covering all three files, the directory base, three child entries and the existing parent's new entry, plus reserve. The receipt stores exact argv, cwd, three-key launch environment, native limits/result, input and capture hashes. It is an observation receipt, with no controller-completion authority. Partial failures are uploaded as ineligible evidence.

Capture adapters use descriptor-relative exclusive creation and inode-bound stat calls while retaining no-follow ancestor/root descriptors. Capture reads, receipt writes, marker validation and descriptor close all recheck exact ownership. Every source and both contracts are hashed before and after the child. The selected interpreter executable/version is checked on both sides using the pinned observer function. Full stdlib fingerprint refresh remains false.

The upload marker requires the successful observation and upload steps, exactly three local evidence files, strict single-record stdout, empty stderr, matching receipt and exact upload output shapes. It binds stdout and receipt hashes, both contract hashes, run/attempt/commit and the uploader-returned artifact identity. Terminal/API/ZIP reconciliation is still required; upload outputs alone are not authenticated terminal evidence. The marker makes no profile approval or guard-execution claim.

Receipt and work-directory fsync do not establish whole-tree crash durability for the capture files or the new work-root entry in its parent. Terminal reconciliation verifies the actual retained artifact bytes.
